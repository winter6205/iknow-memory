# 0012. Durable corpus index-job orchestration: per-source job binding, the content_identity column, and the async MCP job wire

Date: 2026-09-25
Status: accepted

## Context

A permanent corpus upload lands as text first; the graph work behind it (extract → projection → **Leiden** → community summaries) is long-running, and corpus-wide **检索档** C readiness is a whole-graph fact. `source_documents.status = ready` means only “the last push landed and ≥1 **chunk** exists” — never graph or C readiness. MCP offers the caller no notification primitive and one synchronous result per call, so a durable job cannot be a longer-running **extract_triples** call, and fin needs an identity that survives an iknow-memory restart plus a way to report graph/C readiness without inferring it from a successful push. The four decisions below close that gap, and item 5 records the fin seam they produce. `specs/corpus-index-job-orchestration.md` owns the full contract, the code facts it is pinned to, and the error tables; this ADR records the one-way doors and the alternatives that were rejected, so no later reader silently reopens them.

## Decision

1. **The idempotency identity is a column, not a fold (choice C).** `source_documents` gains `content_identity text NULL` with a unique index on `(source_ref, content_identity)`, added through the existing forward-compat ALTER path and backfilled lazily by the next push (a legacy NULL row stays readable and retrievable, it simply has no job identity). `chunks.id` keeps its existing derivation `sha256(JSON([source_ref, content_identity]))`; the constraint now enforces what was an assumption. The stored value is computed inside iknow from the whole pushed 资料 body, so no identity field crosses the write wire. _Rejected:_ (A) folding the pair into `chunks.id` only — a durable job cannot be keyed on a derived row id with no queryable source-level identity; (B) a side table keyed by the pair — a second source of truth for a concept the 资料 row already owns (ADR-0001 / ADR-0010).

2. **One job vocabulary: the four C values (choice A).** The `index_jobs` ledger uses exactly `in_progress / ready / failed / stale`. Queued vs running is `started_at IS NULL` vs non-null, never a fifth state word; a `failed` job carries a typed `failure_code`. `source_documents.status` keeps exactly `in_progress / ready / failed` (no `stale`) and its meaning is unchanged. _Rejected:_ (B) a five-state vocabulary adding `queued` / `running` — it forks a near-identical vocabulary beside `community_index_state`; (C) reusing `source_documents.status` as the job state — that column is the text-push status, its CHECK is pinned to three values, and it binds `source_ref` alone while a job binds the pair.

3. **A job binds one source, and the corpus-C mapping is explicit.** `job_id` is derived from the `(source_ref, content_identity)` pair, so re-submitting the pair joins the same job and a different `content_identity` is a new job version that moves that source's prior `ready` job to `stale`; two uploads never coalesce. A job arm that commits graph rows demotes corpus C to `stale` inside that same transaction — the existing extract pipeline's demote path, not a second one — and C returns to `ready` only when the whole summary generation is atomically swapped, so job `ready` and C `ready` are correlated but never identical. Concurrent jobs must not interleave a partial summary generation. _Rejected:_ a coalescing job across uploads — the “which uploads did this cover” reconciliation would have to live in the ledger for no product gain; a corpus-level batch job stays a separate ticket, not an edit to this binding.

4. **Async over MCP is submit + poll on ordinary `tools/call`.** `submit_index_job` persists the job row **first** and returns the durable `job_id` immediately, running no stage inline and blocking on nothing; `poll_index_job` reads the persisted state and a **separate** `community_index_state` sub-object, so the two readiness meanings never share a field. Failure exits are named literals in the `read_source` style — `index_job_invalid_locator`, `index_job_unknown_source`, `index_job_identity_mismatch`, `index_job_unknown_job`, `index_job_in_progress` — never an empty success. This narrows `specs/mcp-tool-surface.md` assumption 9’s “Not a job queue” exclusion to `extract`, `ingest`, and `push`; `extract` itself stays synchronous and is not redefined. _Rejected:_ an in-process-only trigger with no persisted identity, such as reusing the synchronous `extract` tool as the whole job — it cannot survive an MCP process restart and cannot be polled by a host that did not submit it in the same connection.

5. **The fin seam.** fin owns the upload, the raw object, deterministic chunking, and `push`; iknow owns the `content_identity` column, the job ledger, and corpus-wide graph/C readiness. After a successful push fin submits (or joins) the job for the pair and gets the durable `job_id`; it then reads job state and corpus C through the poll tool, and may report graph/C readiness **only** as a pass-through of iknow's corpus-level result. A successful `push`, or a partial or `stale` job, must never be rendered as graph/C ready. Recovery after a fin restart is re-polling the same `job_id`, never re-pushing a different source version.

## Consequences

- One `(source_ref, content_identity)` key now serves push idempotency, job identity, and the fin re-push key: three consumers, one authority.
- A submitted job survives an iknow restart and is observable by a host that did not create it, because queue state is Postgres state, not process state.
- `push` keeps its old meaning exactly: nothing in the write path implies graph or C readiness, and a queued job never rewrites `source_documents.status` or demotes `community_index_state`.
- The MCP catalog grows by two tools and the frozen `tools/list` set is amended by the note in `specs/mcp-tool-surface.md` SC1. Stage execution stays inside iknow-memory's graph-index boundary; no third job-facing surface is added.

**Does not decide:** whether the CLI-only projection-drain and community-summary stages are lifted into a callable module or invoked through their CLI entries, and job-row retention / pruning for `ready` and `stale` rows — both remain open questions of the owning spec.

Considered Options: keeping the identity folded into the derived `chunks.id` only; a side table keyed by the pair; a five-state vocabulary adding `queued` / `running`; reusing `source_documents.status` as the job state; a job that coalesces several uploads; an in-process-only trigger with no persisted row. Each is rejected above.
