# 0013. Entity-merge embedding cap: a pre-declared, source-wide lifecycle budget counted at the merge gate

Date: 2026-10-16
Status: accepted

## Context

*Revised 2026-10-16 after the second architecture gate, which cleared clusters C1–C7 and blocked on one concern (B1). This revision adds: the promote lifecycle as a second budgeted shape (decision 1A); the `E`/`T` derivation moved into `persist.ts` as one exported function (decision 2A); the withdrawn alias exception, replaced by a corrected argument (decision 2); the fail-closed budget handle that replaces a justification the gate found false (decision 3); the promote breach surface (decision 4A); the mandatory `id` tiebreaker on the keyset cursor and the removal of the zero-progress early exit (decision 1). Nothing an earlier review cleared was reopened. Design freeze recorded before implementation: no code has landed.*

Indexing one source can make an unbounded number of merge-gate resolutions, and nothing in iknow-memory names or bounds it. The work is N+1 by construction: `l2DescGate` embeds once per same-type candidate (`src/core/entities/merge.ts:197-204`), `l3NameDescGate` embeds the incoming entity once and then each candidate that lacks a stored vector (`merge.ts:248-251`, `merge.ts:386-392`), and the candidate set is every non-retired entity with no `LIMIT` (`src/core/extraction/persist.ts:629-634`), reloaded once per endpoint resolution (`persist.ts:538`). Per source the cost is `outputs × gates × candidates`, and the fin demo seed needs that cost to be a **number an operator can predict before indexing**, not a surprise discovered as a stalled job.

Two obstacles are structural rather than arithmetic. First, `processBatch` loops the chunk list (`src/core/extraction/pipeline.ts:344`), `processChunk` opens one transaction per chunk (`pipeline.ts:440`) and reaches `persistOutputs` (`pipeline.ts:515`), and the first merge inside that function is `resolveEndpoints` → `mergeEntitiesWithGating` (`persist.ts:198`, `persist.ts:541`). **Extraction and merge are interleaved per chunk, so at the moment a cap would be computed, the rows describing this source's output do not exist yet** — the function that would create them is the function that merges. Second, the production caller is not one chunk page: `runExtractStage` loops, feeding `processBatch` one `deps.batchLimit` page at a time (`src/cli/index-job-worker.ts:346-381`, default page 100 at `src/config.ts:102`), so **a cap scoped to the caller's batch is a cap per page, and a 300-chunk source would derive three of them** — the multiplication the ticket forbids.

**A third obstacle, found by the second gate (B1): `persistOutputs` has a second production path that belongs to no extract lifecycle.** It has exactly two call sites — `pipeline.ts:515` and `src/core/extraction/actions.ts:175`, inside `promoteRecord` — and `promoteRecord` runs the identical `resolveEndpoints` → `resolveEntity` → `mergeEntitiesWithGating` chain (`persist.ts:198`, `persist.ts:541`), so it spends real merge embed requests. It is reachable from **two** entries, the CLI `--promote` flag (`src/cli/extract.ts:609`, dispatched at `:438-439`) and the dashboard `promoteWriteHandler` (`src/dashboard-api/handlers/maintenance.ts:191`, whose deps are built by `persistDeps()` at `maintenance.ts:62-70` returning only `{ embedder, logger, slotEmbedding }`). An operator promoting a judge-held proposal was therefore an **unbudgeted merge path**, and the first revision of this ADR justified a *required* budget field with the premise that "every lifecycle owner constructs one" — a premise that is false, because `persistDeps()` is exactly such an owner and constructs no budget. An incomplete caller enumeration is the same defect class the first gate's C1 found.

`specs/qa-t2-entity-merge-embed-cap.md` owns the resulting behavior contract, including the complete five-entry `persistOutputs` production enumeration; this ADR records the one-way doors and the rejected alternatives. This is a design freeze recorded before implementation: no code has landed.

## Decision

1. **The lifecycle is one `source_ref` × one extract-stage run, and it consumes that source's whole pending set.** Phase E extracts every chunk of the lifecycle's scope and stages `{ chunkId, outputs }`; the cap is derived once from that population; phase C commits chunk by chunk with the existing one-transaction-per-chunk shape. The cap is therefore knowable up front, which is the only property that makes a breaker a breaker. `runExtractStage`'s rescan loop becomes the **phase-E page loop** — the same pending scan, the same page size, but a keyset cursor on `(created_at, id)`, because phase E commits nothing and a repeated pending query would hand back the same chunks forever. **That cursor is a modification of both existing scans, and the `id` tiebreaker is mandatory rather than cosmetic:** both order by `ORDER BY c.created_at` with no tiebreaker today (`pipeline.ts:144`, `pipeline.ts:210`), and `created_at` is demonstrably not unique — the repo already works around same-`created_at` ties making an `rn = 1` partition winner non-deterministic (`pipeline.ts:129-131`). Without the `id` term a page boundary can land inside a tie group, and either `>` silently drops the rest of that group from the lifecycle or `>=` extracts it twice. `EXTRACT_ROUND_CEILING` (`index-job-worker.ts:123`) survives as a bound on phase-E pages and keeps its `INDEX_JOB_EXTRACT_INCOMPLETE` code; the stall it guarded (a batch that indexed nothing leaving its chunk pending) is structural under the new shape. **The zero-progress early exit `notIndexed(summary) > 0 -> break` (`index-job-worker.ts:380`) is removed,** because its stated justification — that a rolled-back chunk stays pending so a rescan hands back the same batch instead of draining it (`index-job-worker.ts:369-375`, and `EXTRACT_ROUND_CEILING`'s own doc comment at `:118-122`) — describes a rescan that no longer exists, and because keeping it would make the lifecycle's *scope* a function of extract outcomes, shrinking `E`, `T` and `N` at the first all-self-loop page. Only `|| !scan.hasMore` and the page ceiling survive. The cost is declared: a source whose first page is entirely non-indexing now pays phase-E round trips across its whole pending set, and its `failed` / `writeFailures` tallies (`index-job-worker.ts:376-377`) now cover the whole source. The two other callers — `cli/extract.ts:490` and `tools/extract.ts:518` — hold source-agnostic selections (`pipeline.ts:112-152`, `pipeline.ts:160-181`) and therefore **partition** by source: one `SELECT DISTINCT c.source_ref` over their selection, then one lifecycle per source. The partition key is resolved by the caller, so `ChunkInput` (`extract.ts:40-43`) gains no field and `processBatch` still cannot see a `source_ref`; the consequence is that a mixed-source selection now yields N lifecycles and N `batchId`s where it yielded one. _Rejected:_ **(A) scope the lifecycle to the caller's chunk page** — this is the defect: the production caller loops (`index-job-worker.ts:346-381`), so a page scope multiplies `entities + triples + chunks` by the page count and inflates the budget in proportion to the fan-out being bounded; **(B) query persisted pre-merge rows** — the plan forbids it and it is physically impossible: those rows are created *by* the merge path, and the only pre-merge rows available are corpus-wide entity rows from earlier sources, which say nothing about this source's output count; **(C) keep streaming and derive the cap from a running count** — a cap derived from the spend it is meant to bound reports the blow-up after paying for it, which is a post-mortem, not a breaker; **(D) stage to a table or to disk** — no precedent in the extract path and a second durability surface that rollback must reconcile.

1A. **`promoteRecord` is its own single-record lifecycle, budgeted by the same formula with `N = 1` (B1's resolution).** It runs the same `resolveEndpoints` → `resolveEntity` → `mergeEntitiesWithGating` chain (`persist.ts:198`, `persist.ts:521-548`) and spends real merge embed requests, but belongs to no extract lifecycle: no extract stage, no `source_ref` scope, no `batchId`, no page loop — it opens `BEGIN` at `actions.ts:126`, locks one record (`:128-131`), reads one chunk (`:164-174`) and replays `parsed.data.triples` (`actions.ts:175-182`). Its population is a payload sealed by an earlier run, so it has **no phase E**; the sealed `proposed_payload` *is* the pre-merge population and is in hand before any merge work runs, so the cap is still pre-declared. `E` and `T` come from those held triples by the identical filter and key terms, and **`N = 1`** because it commits exactly the one chunk it read: `embed_cap = E + T + 1`, from the **same exported derivation** as the extract lifecycle (decision 2A), on the same shape (`judge.ts:181-182`, `.min(1)`; `types.ts:20-26`). **No new formula, no promote-specific ceiling.** Arming sits between the payload parse (`actions.ts:148-158`) and `persistOutputs` (`:175`), which the existing code order already permits. **The CLI `--promote` entry (`cli/extract.ts:438-439`, `:609`) and the dashboard entry (`maintenance.ts:187-194`) are one semantic, not two:** same cap, same derivation, same breach class. _Rejected:_ **leaving promote unbudgeted** — an operator replay would be an unbounded merge path; **a separate promote cap** — a second formula is what the `E + T + N` freeze forbids; **routing promote through an extract lifecycle** — there is nothing to extract.

2. **The formula stays; its terms are defined once and for all.** `embed_cap = E + T + N` with `E` = distinct `(role, normalized name, normalized closed-set type)` endpoint identities, `T` = distinct `(normalized head, normalized tail, normalized raw relation)` identities, `N` = lifecycle chunks that reached phase C. The type term is `types.headType` / `types.tailType` from `resolveClosedSetTypes` (`persist.ts:336-340`, passed into `resolveEntity` at `persist.ts:299`, `:307`) — the value every gate compares (`merge.ts:124`, `:149`, `:170`) — and never the raw `out.headType`, which reaches no gate. **Deduplication applies to both `E` and `T`** because a repeated surface form resolves by L0 exact-name match at zero embed cost (`merge.ts:143-157`); role stays in the `E` key because a self-pair runs both endpoint resolutions. Ungrounded and closed-set-surviving outputs **count**, because `resolveEndpoints` (`persist.ts:198`) runs before the grounding and self-pair checks (`persist.ts:227-231`, `persist.ts:211-215`). Sealed-failed legs **do not** count; rolled-back write-failure legs **do**, because a rollback cannot refund work already done. No candidate factor is ever added: the N+1 shape is bounded by construction of the population, not by a fudge factor.
   **The "known exception" of the previous revision is withdrawn as factually wrong, and the invariant strengthens.** It claimed that after an L3 merge the incoming surface form survives only as an alias row invisible to `loadEntities`, so a repeat misses L0 and spends again. That is false for L3: an L3 merge materializes a **loser `entities` row carrying the incoming surface form** (`persist.ts:553-565`), `insertEntity` writes it with **`retired = false`** (`persist.ts:787-788`), and `linkMergedEntity` writes **only** `merged_into`, never `retired` (`persist.ts:816-820`), while `loadEntities` filters on `retired = false` **only** (`persist.ts:632`). The alias is irrelevant to L0; the loser row is what keeps the name live, so the repeat still hits `l0Match` (`merge.ts:147-150`) and `resolveCanonicalId` hops it to the survivor (`persist.ts:550`). Every non-merge outcome also lands in the store: `persist.ts:549` gates only on `kind === "merge"`, so created-new, all three reject shapes and the judge hold all fall through to `insertEntity` (`persist.ts:582-587`). **Therefore `embed_calls <= E <= embed_cap` holds unconditionally, with no exception on any path.** The one honest caveat: this rests on `resolveEntity`'s current *write* behavior, not on a structural guarantee in `merge.ts` — a future merge gate that materialized no row (an L2 *merge* would be the natural candidate; today `l2DescGate` can only reject or return null, `merge.ts:190-228`) would reintroduce the undercount, and that is a documented revisit trigger, not a hole in this design.

2A. **The `E` / `T` derivation moves into `persist.ts` as one exported `deriveMergeEmbedCap(outputs, chunks)`; `resolveClosedSetTypes` and `isAliasSelfLoop` stay module-private.** The gate found a hard prerequisite the design had missed: the `E` definition depends on `types.headType` / `types.tailType`, whose producer `resolveClosedSetTypes` (`persist.ts:336`) and its companion `isAliasSelfLoop` (`:343`) are plain non-exported functions, while the derivation point for the extract lifecycle sits in the pipeline / stage adapter — **outside `persist.ts`**. As frozen, `E` was not computable at all. Moving the derivation in keeps one home for the closed-set filter and the count, and makes drift between "what we count" and "what we commit" impossible; exporting the two helpers instead would leak internals purely so a caller could restate the filter, which is the drift the repo's one-home rules already exist to prevent (`PENDING_CHUNK_PREDICATE`, `pipeline.ts:95-103`; `notIndexed` / `batchFailureCode`, `pipeline.ts:279-311`). The promote lifecycle calls the same exported function, which is what lets decision 1A add a lifecycle without adding a formula.

3. **The budgeted unit is one merge-gate resolution, counted at the merge-context seam, and never refunded.** One call to `mergeEntitiesWithGating` (`persist.ts:541`) that issued at least one embed request is one unit. The earlier framing — that `embed_calls` bounds provider requests — is **withdrawn as false**: one resolution issues up to `C + 1` requests against an unbounded candidate store. What holds instead is `embed_calls <= E <= embed_cap` **unconditionally** (decision 2). Counting is structural and local: `ExtractPersistDeps` (`persist.ts:60-87`) carries the lifecycle's budget, and `resolveEntity` wraps `deps.embedder` in a per-resolution counting proxy at the merge-context construction (`persist.ts:541-548`) and passes the proxy, leaving `deps.embedder` untouched for the entity write embed (`persist.ts:562`, `:586`) and the relation-normalization batch (`persist.ts:493-496` → `normalize.ts:81`). **No `merge.ts` call site changes** — the proxy satisfies `EmbeddingClient` (`src/core/embedder.ts:14-28`) and forwards `embed` verbatim (`merge.ts:443`, `:412`, `:390`). One proxy instance per resolution raises the counter at most once, on its first call. A resolution that then fails still counts, and a rolled-back transaction refunds nothing. The per-candidate fan-out inside one resolution — the real cost, and the part that grows with the corpus — is deliberately **outside** the budget: bounding it is the blocking-subset candidate loader's ticket (`merge.ts:104-110`), which this ADR does not decide, and no raw-request counter is added because the frozen field list has no reader for it. The same is true of the relation-normalization embed, so `embed_calls` is worded as *merge-gate resolutions that embedded*, never as all embedding spend.

   **The required budget field is a fail-closed handle, not a pre-computed number, and its previous justification is withdrawn.** The first revision required the field on the premise that "every lifecycle owner constructs one, so no caller can run a merge with no budget" — the gate found that premise false, since `persistDeps()` (`maintenance.ts:62-70`) constructs exactly such an owner and no budget, and since the promote lifecycle's cap **cannot** be known at deps-construction time (it depends on a payload read later). The field is therefore an unarmed→armed→counting **handle** with `arm(cap)`, `countResolution()` and `snapshot()`, and `countResolution()` **throws a typed error while unarmed**. That turns "no caller can run a merge with no budget" from a claim about callers into an enforced invariant, and it is what makes the field safe to require on a path whose cap is derived mid-function. _Rejected:_ **making the field optional** — an optional budget silently restores the unbudgeted promote path; **a fabricated fixed budget for promote** — it would be a number with no relationship to the work.

4. **A breach is a run-level typed failure: `ENTITY_MERGE_EMBED_LIMIT`, propagated, never absorbed.** The (cap + 1)-th resolution is refused before it issues any request — the proxy throws on its first call once `embed_calls >= embed_cap`; the in-flight chunk rolls back; the index-job extract stage re-wraps the error as `IndexJobStageError` (`index-job-worker.ts:347-351`) so `runIndexJob` publishes `failed` with that `failure_code` (`src/core/index-job.ts:107-109`). _Rejected:_ **sealing it as a `failed` chunk leg** — `processChunk` is mark-and-continue (`pipeline.ts:344-370`), so the batch would keep spending and the code would reach the operator through `batchFailureCode`'s precedence (`pipeline.ts:308-311`), reading a cost failure as a content failure; **degrading it to a skipped candidate** — the gates already treat an unprovable embed as "skip and fall through to `created-new`" (`merge.ts:205-210`, `:255-259`), which would publish a plausible graph from merges that were never proven; **leaving it untyped** — an untyped throw is rethrown by `runIndexJob` (`index-job.ts:108`) and leaves the row reclaimable (`index-job-worker.ts:263-271`), which is the wrong answer for a named, actionable failure. The literal already exists on the fin side (`fin/src/fin/corpus/demo_seed.py:175`) and is adopted unchanged.

4A. **The promote lifecycle's breach is the same literal, thrown typed, surfaced through existing plumbing.** It has no index job, so decision 4's re-wrap has no target: the throw escapes `promoteRecord`, the single transaction rolls back (`actions.ts:215-218`), and the record stays `failed` with its payload — the retry posture the function already documents (`actions.ts:111-112`). It is **not** folded into `commitSelfLoopRejection` (`actions.ts:183-197`), because a cost refusal is retryable and that permanent reject is not, and because the operators told never to re-run a self-loop are the same operators who must be able to retry this. It is **not** a `PromotionRefusedError` either: those mean "this record cannot be promoted" and carry `INVALID_INPUT` (`actions.ts:37-42`, `:133-174`), which would read a cost refusal as a caller mistake. Surfaces reuse the existing routes with no new endpoint and no new exit path — the CLI through `runCli`'s catch → `reportFatal` → exit 1 (`cli/extract.ts:597-614`), the dashboard through the shared `mapRunnerError` (`maintenance.ts:179-180`, `handlers/writes.ts:130`), which sends any non-`INVALID_INPUT` `GraphragError` to 503 (`handlers/writes.ts:116-118`). The breach line keeps the frozen three fields; `source_ref` on this path is the promoted chunk's, so the chunk read gains that one column (`actions.ts:164-167`; the column exists and is already read from this table at `pipeline.ts:208`).

5. **The observable surface is a log line and nothing else.** The breach logs `entity-merge-embed-limit` at error with exactly `{ source_ref, embed_calls, embed_cap }` (SC10-safe: `src/logging.ts:12-22`), and the per-lifecycle completion line carries `embed_cap` and `embed_calls` so a cap is observable on runs that **do not** breach, which is what makes a deployment check possible at all. **Both lifecycle shapes log the same three fields**, so `promote-record-complete` (`actions.ts:209-214`) gains `source_ref`, `embed_cap` and `embed_calls` too — one vocabulary, one reader, no fourth field. **No durable column is added.** `index_jobs` has `failure_code` and no detail column (`schema-bootstrap.ts:589-598`); nothing reads `embed_calls` or `embed_cap` from durable state — fin's port type carries only `failure_code: str | None` (`fin/src/fin/retrieve/index_job_port.py:177`, `:195`) and its classifier branches on the code alone (`fin/src/fin/corpus/demo_seed.py:1718`) — and a column would force a migration *and* change `poll_index_job`'s wire shape (`src/tools/index-job.ts:47-48`) for zero read demand. The ticket asks for logs, and logs are the whole surface. **No `ceiling` alias either:** the ticket's "retain `ceiling` if a consumer still needs it" is conditional, no consumer needs it, and since the breaker was never released no consumer ever read it, so an alias-removal trigger would be unobservable. _Rejected:_ **an alias** — it would be a conflict between two of our own drafts, not a compatibility requirement; **a durable detail column** — YAGNI against a read demand that does not exist.

6. **Partial commit stays; a source-wide rollback is refused.** One transaction per chunk (`pipeline.ts:440`) means chunks committed before the breach remain committed and only the in-flight chunk rolls back; rolling the source back would erase real committed work and invent an atomicity unit this pipeline does not have. A reclaimed job starts a **new lifecycle** over the still-pending chunks, with its own cap — the budget is per-lifecycle in-process state, never a module singleton and never a database row, so concurrent runs cannot share a counter and no lock is introduced.

7. **Phase E owns no transaction, and every artifact it produces has a named owner.** Today the `extraction_records` row (`pipeline.ts:442`), the method-conflict gate (`pipeline.ts:451`), the LLM call (`pipeline.ts:471`), the judge (`pipeline.ts:490`), `markFailedWithProposal` (`pipeline.ts:496`) and `persistOutputs` (`pipeline.ts:515`) share the single `BEGIN` at `pipeline.ts:440`. Frozen: a sealed-failed leg writes its failed record and its judge proposal in a **dedicated single-row transaction committed at the seal** (where `pipeline.ts:477` and `:502` commit today), so a crash during phase E never loses a failure record; the `ok` leg's record row is created in phase C inside the chunk transaction, in today's position; every merge-side write (`persist.ts:558-588`, `pipeline.ts:530`, `:532`, `:576`, `:581`, `:593`, `:594`) stays in the chunk transaction; and the method-conflict gate runs in **both** phases — phase E only to avoid paying a model round trip for a chunk that will be refused, phase C to keep the guard at the commit point. A consequence is welcome: the write transaction no longer spans a model round trip. The cost is declared, not hidden — see the reclaim regression below.

## Consequences

- The cost of indexing one source becomes a number derived from that source's own extracted population, published before the merge work runs — the seed operator can predict it, and a change that inflates it shows up as a breach instead of as a stalled job.
- **The maintenance lane is now inside the breaker, which is a behavior change operators will notice.** A judge-held `proposed_payload` sealed by any earlier run carries no cap from its own sealing, so its first promotion is budgeted for the first time at replay — and a promotion that breaches rolls back and stays retryable (`actions.ts:215-218`), so retrying it breaches again until the source changes. Accepted: an uncapped replay is the hole the breaker exists to close, and the record is never left in a half-promoted state. The promote path stages nothing and so is not subject to the phase-E staging ceiling — it holds one already-persisted payload and one chunk.
- **`E` is no longer an undercount, so the invariant is stronger than the previous revision claimed** — `embed_calls <= E` holds on every current path (decision 2). What is weaker is its durability: it depends on `resolveEntity` continuing to materialize a live row for every incoming surface form, which is a property of the write path, not of `merge.ts`.
- **Removing the zero-progress early exit trades early termination for a frozen scope.** A source whose first page indexes nothing now pays phase-E round trips over its whole pending set, and its outcome tallies cover the whole source rather than stopping at the first zero-progress page. In exchange the lifecycle's population can no longer shrink because of an extract outcome, which is what keeps a re-derived cap from being quietly lower than the work ahead of it.
- Extract/merge interleaving is replaced by a staged extract phase for the merge path only. Phase E stages output JSON and **not** chunk text; phase C re-reads `chunks.content` by id inside its own chunk transaction, because the grounding gate (`persist.ts:227`, supplied at `pipeline.ts:519`) and the enrichment leg (`pipeline.ts:563`) both need it. The staging bound is therefore in **bytes** — `GRAPHRAG_MEMORY_ENTITY_MERGE_STAGE_MAX_BYTES`, default 64 MiB — checked at every phase-E page boundary before the next page's extraction. This replaces a chunk-count ceiling that was unreachable in production (the production page is 100, `config.ts:102`) while describing ~100 MB of chunk text at `DEFAULT_MAX_CONTENT_LENGTH = 100_000` chars (`extract.ts:33`): a ceiling nobody could hit that everybody would assume they had. The refusal reuses `ENTITY_MERGE_EMBED_LIMIT` with a scope-shaped message, because fin's classifier branches on the code alone (`demo_seed.py:1718`) and the operator action — raise the knob or split the source — is the same one a cost breach asks for. A distinct public literal would have needed a new fin class for no new decision.
- **A reclaim regression, declared and accepted.** During phase E nothing is persisted for `ok` legs, while the lease is 15 minutes by default (`index-job-worker.ts:125`) and the claim happens *before* the serialization lock is taken (`index-job-worker.ts:218`, `:259`). A lifecycle whose phase E outlives the lease is claimed by a second worker, which blocks on `JOB_SERIALIZATION_KEY` while the first finishes; the first worker's terminal UPDATE is then refused (it is guarded by the `started_at` it claimed, `pgvector-backend.ts:1804`) and the second worker re-extracts the source, **doubling the phase-E LLM spend**. Today's exposure is one chunk — one transaction, one model round trip; the new exposure is one source's entire phase E. The mitigation is the operator's `--stalled-after` flag (`index-job-worker.ts:183-196`), which already exists. A lease heartbeat is rejected here (it needs a new touch path on the store and fights the `started_at` publish guard) and committing per page is rejected as the forbidden per-batch cap. A source whose phase E cannot finish inside the lease must have the flag raised; the breaker will not absorb that silently.
- The cap bounds **one lifecycle**. A pathological source re-run after a reclaim gets a fresh cap over the remaining chunks, so repeated re-runs are not a single bounded spend; bounding that needs a durable per-source spend ledger, which is a separate ticket and is deliberately not added here.
- The L2/L3 per-candidate fan-out and the relation-normalization embed (`normalize.ts:81`) remain uncapped by design. A workload whose cost is dominated by a large candidate store or by unmapped relation surface forms is therefore still outside this breaker; `embed_calls` is worded to prevent either from being misread.
- `extraction_records.batch_id` now groups a whole source's rows under one lifecycle id rather than one id per 100-chunk page, and a mixed-source caller selection now produces one lifecycle per source. Both are visible ledger-shape changes, accepted because the alternative is a per-page cap.
- A breach leaves the source partially indexed by design (earlier chunks committed, remaining chunks pending) and the job `failed` with a named code, readable in the log line. Recovery is the existing pending-chunk path plus an operator decision about the source, not a hidden retry.
- The formula gained no multiplier, and none may be reintroduced as a workaround. Recorded evidence at `ca0feeed`: no ×50 exists in `src/**`, `tests/**`, `specs/**`, `docs/**`, `docker-compose.yml`, `.env.example`, the fin worktree, or a built artifact (`dist/` does not exist in this worktree); the only `50` matches are a UUID version nibble (`src/core/structured/identity.ts:473`), an unrelated comment (`src/core/extraction/fast.ts:20`), and fin's 50 MiB upload cap (`fin/specs/corpus-serve-ingest.md:144`). After the fix merges, the worker must be rebuilt and restarted — it is a long-running drain loop (`src/cli/index-job-worker.ts:203`) — and the running build is proven multiplier-free by the `embed_cap` on an observed run.

**Does not decide:** the blocking-subset candidate loader `mergeEntitiesWithGating` still refuses (`merge.ts:104-110`); job-row reset/re-arm semantics, which stay with fin T3 and ADR 0100; any change to merge thresholds, candidate rules or decision kinds, all of which are inherited unchanged from `specs/graph-index-standard-fast.md` and `specs/merge-gray-zone-judge.md`; the semantics of `resolveClosedSetTypes` / `isAliasSelfLoop`, which stay module-private behind `deriveMergeEmbedCap` (decision 2A).
