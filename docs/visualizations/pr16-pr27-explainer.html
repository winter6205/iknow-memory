1 · 这是什么项目？为什么需要「抽取管线」？

iknow-memory 是什么

iknow-memory 是一个通过 MCP（Model Context Protocol）协议暴露给任何 host 的外置知识记忆服务。 它只提供两个 MCP 工具：ingest（把文本切成 chunk、向量化、写入 chunks 表） 和 retrieve（cosine 检索 + valid_window 时间切片）。 host（Claude Code / iknow harness / 自定义 agent）负责上下文工程——JIT 触发、cache 布局、上下文组装。 （来自 README.md）

「不做上下文工程」是核心定位：server 只保证"存得对、查得准、可时间切片"。 学习对象是 gbrain——目标是继承其优点（混合检索 / 分层记忆 / bi-temporal），改进其缺点（三元组抽取、canonical 实体合并、PPR 多跳、社区检测）。

P0 之前缺什么？

截至 0.0.0，stage 0+1 已完成：chunks-only ingest/retrieve + 向量 cosine + valid_window 时间切片。

但 P0 规划指出：「gbrain 没有 LLM 三元组抽取，也没有 canonical 实体合并——这是 BrainBench +31 P@5 的源头」。 也就是说，当前能存 chunk、能按相似度查，但查不到"Alice 工作于 Acme"这种带语义的事实三元组，也没有"Alice / Alice Smith / A. Smith"合并到同一个 canonical 实体的能力。

本组 PR 解决的正是 P0 的两个 ROI 最高的工作流：抽取 + 合并。

7 · canonical 实体合并：四道门怎么决定 "Alice" == "Alice Smith"？

核心代码：src/core/entities/merge.ts。 对一个 incoming 实体依次问 4 个问题，第一个 yes 即返回决定；全失败 → "created-new"。

L0 规则精确

normalized name 完全相等 + type 相同 → 合并

name.toLowerCase().trim() === name'

不需要 embedding（cost = 0）

L1 类型拒绝

normalized name 相同但 type 不同 → 拒绝 + 灰区日志

reason: "type-mismatch"

一个实体不能同时是两个 type

L2 描述 cosine 地板

同 type 后，描述 cosine < 0.30 → 拒绝

descCosine < config.l2DescLowThreshold

描述 < 8 字符则直接进 L3

L3 name+desc 合并阈值

canonical_name + " | " + description 的 cosine ≥ 0.50 → 合并；否则灰区拒绝

cosine ≥ config.l3NameDescHighThreshold (0.50)

默认 single-floor；bandMode 可开（低阈值 0.30）

merge.ts 的核心循环（≤40 行 / 嵌套 ≤2 的复杂度信封） 
export async function mergeEntitiesWithGating(
  incoming, candidateSet, ctx
): Promise<MergeOutcome> {
  const config = ctx.config ?? DEFAULT_MERGE_CONFIG;
  const candidates = candidateSet === "all" ? [] : candidateSet.map(c => ({...c}));
  const log = ctx.logGrayZone ?? defaultGrayLog;

  const l0 = l0Match(incoming, candidates);          if (l0) return ...;
  const l1 = l1TypeReject(incoming, candidates, log); if (l1) return ...;
  const sameType = candidates.filter(c => c.type === incoming.type);
  if (sameType.length === 0) return { canonicalId: "", decision: "created-new" };
  const l2 = await l2DescGate(incoming, sameType, ctx, config, log); if (l2) return ...;
  const l3 = await l3NameDescGate(incoming, sameType, ctx, config, log); if (l3) return ...;
  return { canonicalId: "", decision: "created-new" };
}

8 · relation 归一化：LLM 说 "works at" 怎么变 "works_for"？

核心代码：src/core/extraction/normalize.ts。4 级级联，每级代价/精度不同：

① exact
case-insensitive exact match against ALLOWED (36 项)
→
② synonym
ALIASES 表 (15 条：works at → works_for)
→
③ embedding
cosine vs 36 项， best match ≥ 0.7
→
④ UNMAPPED
合法 sentinel，留作待审

为什么是级联而不是一个分类器？前两级 O(1) 决定论；embedding 是 O(N·dim) 模糊匹配； 严格级在前保证常见 case 拿到稳定的图遍历 key，模糊级兜底 LLM 表面漂移。

9 · LLM 失败时怎么办？retry 分类表

核心代码：src/core/extraction/llm-client.ts。#4 D4 决策 + T8 异常边界补丁。

失败类型 HTTP 状态 重试策略 最终结果 含义
5xx 5xx / 网络错 / 无 status 3 次，指数退避 100→200→400ms（封顶 2s） kind: "5xx" → mark-and-continue 服务端暂时性故障
4xx 4xx（除 429） 不重试，单次失败 kind: "4xx" → mark-and-continue 请求结构错，重试无用
429 429 SDK 内部自动重试；外溢按 5xx 处理 同上 rate limit，已在 SDK 层处理
format 200 但 JSON 不合规 1 次重试（2 次 LLM 调用），用 zod 校验 kind: "format" → mark-and-continue 内容错但通道通，重发有概率成功
exception SDK 抛异常（任何原因） 被 extractChunk try/catch 兜底 kind: "failed"，code=LLM_EXCEPTION T8 防御补丁：throw 不能 abort 整批

所有失败都被 "mark-and-continue" 吸收：写一条 extraction_records.status='failed' + error_code/error_msg， 批处理继续跑下一个 chunk。listFailed() 暴露失败清单，--only-failed 单独重试。

10 · 写层 dedup：相同 fact 第二次来时怎么办？

核心代码：src/core/extraction/dedup.ts。#4 D6 + A9 调和。

  • dedup key = (head_id, relation_norm, tail_id) + valid_window 重叠
  • 无 DB 层约束——spec-1 Open Question 2 拍板为应用层
  • 重叠语义：Postgres 的 tstzrange && 重叠算子，左闭右开 [)

12 · CR High #2 修复：LLM 自由类型 → DDL 封闭 4 项

问题：spec-1 DDL 给 entities.type 加了 CHECK 约束，只允许 person / concept / system / event。 但 LLM 自由发挥，可能输出 "Organization" / "Location" / "Tool" 等任意字符串。 直接 INSERT 会被 CHECK 拒绝 → 整 chunk 事务 ROLLBACK → write-failure → exit 2。

修复（commit ac02fcd，CR High #2）：CLI 边界加 normalizeEntityType() 映射器： 

person    ← person, human, individual, user, agent
concept   ← organization, company, team, group, org, concept
system    ← system, tool, platform, service, location, place, system_component
event     ← event, incident, occurrence, action
concept   ← 任何其他 / 空 / 未知（fallback，info 级别日志记录）

"Organization → concept" 不是完美映射（P0 schema 不区分公司与概念）， 但 4 类封闭集合是契约；落入 concept 桶会在 info 日志里留下可审计痕迹。
