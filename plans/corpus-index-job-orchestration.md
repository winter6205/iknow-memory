## Settled contract and persist list

- `push` stores fin-cut text and makes a source searchable independently of graph extraction. The current `source_documents.status = ready` means the last push succeeded and at least one chunk exists; it does not mean graph extraction or C summaries are ready.
- Graph extraction remains a separate index operation. The MCP `extract` tool is currently synchronous, processes selected pending chunks, and is not a durable job queue. The community-summary runner is a separate CLI entry point.
- C readiness remains global: `community_index_state` describes the whole projected graph and summary generation (`in_progress`, `ready`, `stale`, or `failed`); it is not a per-document flag. C stays unavailable until the complete summary generation is ready, while the text-search and graph arms retain their existing behavior. The upload's source/version job outcome and this global C state are distinct facts whose mapping must be explicit in T1.
- **Settled 2026-09-25 (T1 decisions — contract pinned in `specs/corpus-index-job-orchestration.md`):**
  1. **Idempotency key (chosen C):** a real `content_identity text NULL` column on `source_documents` with a unique constraint on `(source_ref, content_identity)`; the pair is elevated from the implicit invariant folded into derived `chunks.id` to a constraint-enforced source identity. Backfill is lazy on re-push; the fin wire is unchanged.
  2. **Job-state vocabulary (chosen A):** the new index-job ledger reuses `in_progress / ready / failed / stale` from `community_index_state`; `queued` vs `running` is `started_at` null/non-null. `source_documents.status` is **not** changed and keeps `in_progress / ready / failed`.
  3. **Binding granularity:** a job binds a single `{document_id, version}` source (one `source_ref`, one `(source_ref, content_identity)` pair) and never coalesces across uploads; an explicit per-source-job ↔ corpus-level-C mapping is written in the spec (graph change demotes C to `stale`; only the atomic summary swap returns C to `ready`).
  4. **MCP async job wire:** a submit tool persists the job and returns a durable `job_id` immediately, plus a separate poll tool reading persisted state; this amends `specs/mcp-tool-surface.md`'s "not a job queue" exclusion only for the new job tools, while `extract` stays synchronous.
- **Persist list:** `index job` and C readiness already exist in the graph-index contract. T1 now records the selected public status vocabulary and ownership terms in `specs/corpus-index-job-orchestration.md`; the CONTEXT glossary entries (`index job`, `content_identity`, the text-vs-graph readiness split), the new ADR, and the `mcp-tool-surface.md` supersede note are queued in that spec's 待写入 list and land with the implementation, not before.
