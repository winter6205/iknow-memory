## Goal

One source's extraction run must make a **bounded, pre-declared number of merge-gate resolutions**, and that number must be derived from the source's own extracted population — not from a guess about candidate fan-out, not from rows that do not exist yet, and not from the caller's page of chunks.

This spec freezes that lifecycle: the phases, the exact meaning of `entities + triples + chunks`, the counted unit, who consumes the budget, what a breach does, and what the operator observes. The formula itself is **unchanged**; what is new is that it is computed after extraction and enforced before any merge work spends over it.

There are exactly **two lifecycle shapes**, and both are budgeted by the same formula with the same terms: the **extract lifecycle** (one `source_ref` × one extract-stage run, Decisions 1, 6, 8) and the **single-record lifecycle** of `promoteRecord` (one held `proposed_payload`, `N = 1`, Decision 1A). Neither shape has a third variant, and neither is allowed to run a merge-gate resolution without an armed budget (Decision 3).

**Who uses it:** the iknow implementer of the breaker and its tests; the fin seed operator reading a breached job; any reader asking "how many merge resolutions can indexing one document make?".

## Contract

### Decision 1 — the lifecycle: one source's whole pending set, then one commit/merge phase

**A lifecycle is one `source_ref` × one extract-stage run, and it consumes every pending chunk that source has when the stage starts.** Its scope is the *source*, not the caller's page: exactly one cap is derived per lifecycle, no matter how many pages the phase-E scan needs. The lifecycle has two phases:

| Phase | What runs | Merge calls |
| --- | --- | --- |
| **E — extract** | Per chunk: the method-conflict gate (`pipeline.ts:451`), the LLM extract (`pipeline.ts:471`) and `judgeProposals` (`pipeline.ts:490`). Each sealed `ok` leg parks `{ chunkId, outputs }` in memory. **No transaction is open.** | **Zero, by construction.** No entity resolution and no merge gate runs in this phase. |
| **C — commit** | The cap is derived once from the phase-E population (Decision 2), then each staged chunk runs the existing `persistOutputs` path in the same one-transaction-per-chunk shape (`pipeline.ts:440`). | Every merge-gate resolution that issues a request consumes the budget (Decision 3). |

Phase E is what makes the cap *knowable*. A cap that is computed while the merge work it is meant to bound is already running can only ever fire after the blow-up.

**How the scope is reached, and what replaces what.** `runExtractStage` (`index-job-worker.ts:335-386`) today rescans the source's pending chunks and re-enters `processBatch` per page (`index-job-worker.ts:346-381`). Under this decision that loop becomes **the phase-E page loop**: the same scan, the same `deps.batchLimit` page size (`index-job-worker.ts:353-357`, `pipeline.ts:211`), but a **keyset cursor** on `(created_at, id)` rather than a repeated "pending" query — phase E commits nothing, so the pending set is stable while it pages and a repeated pending scan would hand back the same chunks forever. One `batchId` and one `startedAt` per lifecycle (`pipeline.ts:336-338`), not per page.

- **The keyset cursor is a modification of both existing scans, and the `id` tiebreaker is mandatory.** Today both order by `ORDER BY c.created_at` with no tiebreaker (`pipeline.ts:144` for `selectPendingChunks`, `pipeline.ts:210` for `selectPendingChunksBySourceRef`). The keyset form is therefore `ORDER BY c.created_at, c.id` plus `WHERE (c.created_at, c.id) > ($last_created_at, $last_id)`, and **the `id` term is required, not a refinement**: a page boundary can fall inside a group of rows sharing one `created_at`, and with `created_at` alone either `>` skips the rest of that group or `>=` re-reads it, so same-`created_at` chunks would be silently dropped from the lifecycle or extracted twice. The repo already knows `created_at` ties are non-deterministic (`pipeline.ts:129-131`). The `cap + 1` probe that produces `hasMore` (`pipeline.ts:206-217`) is preserved unchanged.
- **The cursor freezes the population at stage start, and that is the scope.** Because the cursor only moves forward and phase E's `ok` legs write no `succeeded` record, the lifecycle is exactly the stage-start pending set: a chunk that becomes pending later (another writer's rollback) or is created later is **out of this lifecycle** and lands in the next run. Accepted, because it is the only way "one lifecycle = one frozen population" and "a re-derived cap never shrinks" can both be true.
- **`notIndexed(summary) > 0 -> break` is REMOVED (`index-job-worker.ts:380`).** Its justification — recorded in the comment at `index-job-worker.ts:369-375` and in `EXTRACT_ROUND_CEILING`'s own doc comment (`index-job-worker.ts:118-122`) — is that a rolled-back chunk stays pending, so a rescan hands back the same batch instead of draining it. Under the new shape that rescan does not exist: phase E advances a cursor and commits nothing, so no page can be handed back, and phase C runs once over the staged set with no loop to exit. Retaining the break would also make the lifecycle's **scope** a function of extract outcomes — the first all-self-loop page would truncate the population and shrink `E`, `T` and `N` — which is precisely the unstable-scope defect this decision exists to remove. Only the other half of the condition, `|| !scan.hasMore`, survives, plus the `EXTRACT_ROUND_CEILING` page bound. **Consequence, stated plainly:** a source whose first page is entirely non-indexing legs now costs phase-E LLM round trips on every remaining pending chunk instead of stopping at page 1, and its `failed` / `writeFailures` tallies (`index-job-worker.ts:376-377`) now cover the whole source rather than stopping at the first zero-progress page. That is the declared cost of a source-frozen scope; it is not absorbed silently.
- **`EXTRACT_ROUND_CEILING` survives, with a changed trigger.** It (`index-job-worker.ts:123`) now bounds **phase-E pages**; a source with more pending chunks than `EXTRACT_ROUND_CEILING × deps.batchLimit` refuses with `INDEX_JOB_EXTRACT_INCOMPLETE` (`index-job-worker.ts:347-352`) before any commit. The stall it used to guard — a batch that indexed nothing leaving its chunk pending, so the rescan loop never drained — is structural under the new shape: phase E commits nothing and phase C runs once over the staged set, so no chunk is ever handed back to the scanner.
- **The batch summary becomes a lifecycle summary.** `IndexJobExtractOutcome` (`index-job-worker.ts:342-382`) keeps its four fields and their meaning; the per-page `extract-batch-complete` line (`pipeline.ts:371`) becomes one line per lifecycle and gains the two cap fields (Decision 7).
- **The other two callers partition; they do not loop.** `cli/extract.ts:490` and `tools/extract.ts:518` hold a selection that can span sources — the corpus-wide `selectPendingChunks` scan (`pipeline.ts:112-152`) and the explicit `selectChunksByIds` path (`pipeline.ts:160-181`) are both source-agnostic. Each caller resolves the distinct `source_ref`s of its already-selected chunks with one `SELECT DISTINCT c.source_ref` over that selection and runs **one lifecycle per source**, in first-appearance order. The partition key is resolved by the caller, so `ChunkInput` (`extract.ts:40-43`) gains no field and `processBatch` still cannot see a `source_ref`. A cap is never shared or summed across sources: a sum would let one cheap source's budget pay for another's fan-out.
  - *Consequence:* a mixed-source selection now runs N lifecycles and produces N `batchId`s where it produced one. That is a visible change to `extraction_records.batch_id` grouping for the CLI's corpus-wide page and for an MCP `chunk_ids` call spanning sources, accepted deliberately — it is the only way a mixed selection can be budgeted at all.
- **The worker path is single-source by construction:** `runExtractStage` takes `sourceRef` as a parameter (`index-job-worker.ts:335-339`) and no code path lets its lifecycle see a second source.

**Rejected alternatives (do not reopen):**

- **(A) Query persisted pre-merge rows.** Explicitly forbidden by the plan, and impossible: at the moment a cap would be computed, the rows do not exist — `persistOutputs` is what creates them, and merge happens inside it (`persist.ts:198`, `persist.ts:541`). The only rows queryable pre-merge are corpus-wide entity rows from *earlier* sources, which say nothing about this source's output count.
- **(B) Keep the stream, compute the cap from a running count, refuse at the end.** Refusing after the fact spends the whole blow-up and then reports it. The breaker has to be pre-declared.
- **(C) Scope the lifecycle to the caller's chunk page.** This is the defect the gate rejected: `runExtractStage` calls `processBatch` once per page, so a 300-chunk source derives three caps and the formula is multiplied by the page count, which the ticket forbids.
- **(D) Buffer to disk / a staging table.** No precedent in this repo's extract path, and a second durability surface to reconcile on rollback.

### Decision 1A — the second lifecycle shape: `promoteRecord`, one held payload, `N = 1`

`promoteRecord` (`src/core/extraction/actions.ts:121-219`) is **its own single-record lifecycle** and is budgeted by **the same cap formula with no new term, no new shape and no second derivation function**. It is enumeration entry 4 and 5 above and it is the path the second architecture gate blocked on.

**Why it is its own lifecycle and not a special case.** It runs the identical `resolveEndpoints` → `resolveEntity` → `mergeEntitiesWithGating` chain (`persist.ts:198`, `persist.ts:521-548`, `persist.ts:541`) and therefore spends real merge embed requests, but it belongs to **no extract lifecycle**: there is no extract stage, no `source_ref` scope, no `batchId`, and no page loop — `promoteRecord` opens `BEGIN` at `actions.ts:126`, reads and locks one record (`:128-131`), reads exactly one chunk (`:164-174`), and replays `parsed.data.triples` through `persistOutputs` (`:175-182`). Its population is already sealed, so it has **no phase E**: the sealed `proposed_payload` *is* the pre-merge population, and it is in hand before any merge work runs.

**The cap, stated with the same terms as Decision 2.** `E` and `T` derive from that record's held `proposed_payload` triples — the same surviving-output filter, the same `(role, normalizeAlias(name), closed-set type)` keys, the same `(normalizeAlias(head), normalizeAlias(tail), relationRaw.trim().toLowerCase())` triple keys, the same deduplication — and **`N = 1`**, because the lifecycle commits exactly the one chunk it read (`actions.ts:164-174`). So `embed_cap = E + T + 1`, computed from the same exported derivation the extract lifecycle uses (Decision 2A), on the same triple shape (`judge.ts:181-182`, `types.ts:20-26`). **No new formula is introduced.**

- **One semantic, two entries.** The CLI `--promote` flag (`cli/extract.ts:438-439`, `:602-614`) and the dashboard `promoteWriteHandler` (`maintenance.ts:187-194`) are **the same lifecycle**: both call `promoteRecord` with a budget, both derive the cap from the same payload with `N = 1`, and both surface a breach the same way (Decision 4A). Neither entry gets its own cap rule, its own multiplier, or a bypass.
- **The cap is armed inside the transaction, after the payload is parsed and before `persistOutputs`.** The ordering is already correct in the code: the payload is read and schema-checked at `actions.ts:148-158`, the chunk at `:164-174`, and only then is `persistOutputs` called at `:175`. Arming sits in that window, so the cap is pre-declared before any merge resolution on every path — the property that makes it a breaker.
- **Degenerate promote populations are already covered.** `ProposalPayloadSchema` requires at least one triple (`judge.ts:182`), so the population is never empty; but every triple can be typed-skipped or an alias self-loop, which yields `E = T = 0` and `embed_cap = 1 > 0` — Decision 2's "zero output, non-zero `N`" case, where the cap is armed, never consulted, and cannot fail a run that made no merge call.
- **Honest consequence — the breaker can now refuse a promotion of a payload sealed before the breaker existed.** A judge-sealed `proposed_payload` from any earlier run carries no cap from its own sealing, so its first promotion is budgeted for the first time at replay. A promotion that breaches is **retryable and will breach again** until the operator changes the source: the throw rolls the single transaction back (`actions.ts:215-218`) and the record stays `failed`, which is exactly the retry posture the function already documents (`actions.ts:111-112`). This is accepted — an uncapped replay is precisely the hole the breaker exists to close — and it is recorded rather than papered over.
- **Rejected alternatives (do not reopen):** **(A) leave `promoteRecord` unbudgeted** — it spends the same merge requests on an operator-triggered path that bypasses every extract scope; **(B) a separate promote-specific cap or a fixed promote ceiling** — a second formula is what the gate's `E + T + N` freeze forbids, and the payload already contains everything the formula needs; **(C) route promote through an extract lifecycle** — there is no extraction to run; the payload was sealed by a different code path (`markFailedWithProposal`, `pipeline.ts:496`) under a judge failure.


### Decision 2 — the formula, and exactly what each term counts

`embed_cap = E + T + N`, derived **once** per lifecycle. No multiplier, no candidate factor, no per-page recomputation. The formula is unchanged; the terms are frozen as follows.

- **Surviving output** = a phase-E `ok` leg's output that passed `resolveClosedSetTypes` (`persist.ts:181-185`) and is not an alias self-loop (`persist.ts:186-190`). Both skipped arms reach no merge gate, so counting them would inflate the cap above the work it bounds. Every surviving output contributes **both** of its endpoints, because `resolveEndpoints` runs before the self-pair and grounding checks (`persist.ts:198` precedes `persist.ts:211-215` and `persist.ts:227-231`).
- **`E` (entities)** = the number of **distinct** `(role, normalizeAlias(name), type)` keys over the endpoints of all surviving outputs, with:
  - `role ∈ { head, tail }`. A self-pair still ran both resolutions, so collapsing the two roles into one key would under-count.
  - `normalizeAlias` the merge module's own normalizer (`merge.ts:87`), because that is what L0 matches on (`merge.ts:147-150`) and therefore what makes a repeat resolution free.
  - `type` the **normalized closed-set** type: `types.headType` for the head key and `types.tailType` for the tail key, as produced by `resolveClosedSetTypes` (`persist.ts:336-340`) and passed into `resolveEntity` (`persist.ts:299`, `:307`). This is the value every gate compares (`merge.ts:124`, `:149`, `:170`). The raw `out.headType` is never comparable and must not be the key term.
  - **Deduplication applies**, because a repeat of the same key resolves by L0 exact-name match at zero embed cost (`merge.ts:143-157`), so counting occurrences would inflate the term while the work did not grow. **The earlier "known exception — the E-dedup undercount" is WITHDRAWN as false; see the corrected argument below.**
  - **Corrected argument — `E` does not undercount, on any path.** The withdrawn exception claimed that after an L3 merge the incoming surface form survives only as an alias row that `loadEntities` cannot see. That is **wrong for L3**: an L3 merge materializes a **loser `entities` row carrying the incoming surface form** (`persist.ts:553-565`), `insertEntity` writes it as `canonical_name` with **`retired = false`** (`persist.ts:791`, `persist.ts:787-788`), and `linkMergedEntity` writes **only** `merged_into`, never `retired` (`persist.ts:816-820`) — while `loadEntities` filters on `retired = false` **only** (`persist.ts:629-634`). The alias row is irrelevant to L0; the **loser row** is what keeps the name live, so the repeat still hits `l0Match` (`merge.ts:147-150`), returns at `merge.ts:116`, and `resolveCanonicalId` (`persist.ts:550`) hops the loser to its survivor. Exhaustive over the seven outcomes of `resolveEntity`:

    | Outcome | Row left carrying `(normalizeAlias(name), closed-set type)` with `retired = false` | Repeat spends? |
    | --- | --- | --- |
    | L0 merge (`merge.ts:155`) | the matched row itself, already in the `retired = false` candidate set | No |
    | L3 merge (`merge.ts:266`, `:348`) | the loser row (`persist.ts:557-563`) | No |
    | L1 type reject (`merge.ts:177-180`) | `insertEntity` on the reject fall-through (`persist.ts:582-587`) | No |
    | L2 desc reject (`merge.ts:217-226`) | same fall-through | No |
    | L3 gray reject (`merge.ts:296-306`) | same fall-through | No |
    | L3 judge hold (`merge.ts:353`) | same fall-through, plus its `name` alias (`persist.ts:588`) | No |
    | created-new (`merge.ts:126`, `:135`) | same fall-through | No |

    A reject or a hold is not a no-insert: `persist.ts:549` gates only on `kind === "merge"`, so every non-merge outcome falls through and inserts the incoming row with its own name and type. The stored type is idempotent on the closed set (`entity-type.ts:39-45`), so the loser's `type` equals the key's type term. **Therefore the first resolution of a distinct key is the only one that can spend, and `embed_calls <= E` holds unconditionally.**
  - **Honest caveat on what that argument rests on.** It is a property of `resolveEntity`'s current *write* behavior (`persist.ts:557-569`, `:580-588`), not a structural guarantee of the merge module — nothing in `merge.ts` requires a merge to materialize the surface form. If a future gate introduces a merge that inserts no row (an L2 *merge* would be the natural candidate; today `l2DescGate` can only reject or return null, `merge.ts:190-228`), the undercount returns and `embed_calls` could exceed `E`. That is a change to revisit this bullet, not a hole in the present design.
- **`T` (triples)** = the number of **distinct** `(normalizeAlias(head), normalizeAlias(tail), relationRaw.trim().toLowerCase())` keys over the surviving outputs, deduped for the same L0 reason. The key uses the **raw** relation surface form, not `relation_norm`, because relation normalization happens in phase C (`persist.ts:232` → `persist.ts:486-497`) and cannot be known in phase E. **Grounded or not**: an ungrounded output already spent both endpoint resolutions before `isGrounded` rejected it (`persist.ts:227-231`), so it counts. A triple that supersedes a prior row (`persist.ts:244-248`) costs no merge work and is unaffected.
- **`N` (chunks)** = the number of lifecycle chunks that **reached phase C**, i.e. every sealed `ok` leg — including an `allSelfLoop` leg, which reaches `persistOutputs` (`pipeline.ts:515`) before the self-loop rejection (`pipeline.ts:531`). A **sealed-failed** leg (LLM failure `pipeline.ts:472-489`, judge failure `pipeline.ts:491-514`) does **not** count: it wrote no triple, resolved no entity and spent no merge work. A **rolled-back write-failure** leg does count, because a rollback cannot refund requests already issued. On the promote lifecycle `N = 1` unconditionally (Decision 1A).

**Degenerate populations are defined, not left to the implementation:**

- **Zero output, non-zero `N`:** `E = T = 0`, so `embed_cap = N > 0`. A source that extracts nothing but commits a chunk keeps a real budget. **No premature cap.**
- **Zero output, zero `N`** (every chunk sealed-failed): `embed_cap = 0`, and it is **inert** — the breach is only ever checked inside a merge-gate resolution (Decision 3), and none runs. The cap is never consulted on this path, so a zero cap cannot fail a run that made no merge call.

### Decision 2A — where `E` and `T` are computed, and the export they require

**Decision: the derivation lives in `persist.ts` as one exported function `deriveMergeEmbedCap(outputs, chunks)`, and `resolveClosedSetTypes` / `isAliasSelfLoop` stay module-private.** This is the prerequisite the derivation has and is stated here as part of the design, not left to the implementer.

The `E` / `T` definitions are only correct if they apply **exactly** the filter `persistOutputs` applies, in the same order: `resolveClosedSetTypes` first (`persist.ts:181-185`), then `isAliasSelfLoop` (`persist.ts:186-190`). Both are plain non-exported functions (`persist.ts:336`, `persist.ts:343`) and `ClosedSetTypes` is a non-exported interface (`persist.ts:326-329`), while the derivation point for the extract lifecycle is in the pipeline / stage adapter — **outside `persist.ts`**. So as frozen, `E` is not computable outside that module at all.

- **Chosen: move the derivation in, do not export the helpers.** `deriveMergeEmbedCap` is exported from `persist.ts` and returns `{ embedCap, calls: 0 }` for a population of outputs and a chunk count; it reuses `resolveClosedSetTypes`, `isAliasSelfLoop` and the module's own `normalizeAlias` internally. Zero new exports of internals, one home for the filter and the count, and no way for the counted population to drift from the committed one.
- **Rejected: exporting `resolveClosedSetTypes` / `isAliasSelfLoop`.** It is the smaller diff and it leaks two internal helpers plus `ClosedSetTypes` into the module's public surface purely so a caller can restate the filter — and a restated filter is a second place for the closed-set rule to drift, which is the same one-home argument the repo already applies to `PENDING_CHUNK_PREDICATE` (`pipeline.ts:95-103`) and to `notIndexed` / `batchFailureCode` (`pipeline.ts:279-311`).
- **Consequence:** `persistOutputs` and `deriveMergeEmbedCap` share one filter implementation, and the promote lifecycle calls the same exported derivation on `parsed.data.triples` with `N = 1` (Decision 1A). A future change to the closed-set gate can no longer desynchronize the cap from the work.

### Decision 3 — the budgeted unit: one merge-gate resolution, counted at the merge-context seam

**The counted unit is ONE MERGE-GATE RESOLUTION** — one call to `mergeEntitiesWithGating` (`persist.ts:541`) that issued at least one embed request. `embed_calls` counts those resolutions within one lifecycle. **The earlier claim that `embed_calls` is an upper bound on provider requests is withdrawn:** it never was one. The cap counts resolution *sites* (`E + T + N` is a count of endpoints and triples) while one resolution issues up to `C + 1` provider requests, where `C` is the whole non-retired entity store, which has no `LIMIT` (`persist.ts:629-634`) and is reloaded per resolution (`persist.ts:538`). What holds instead is the precise statement:

> **`embed_calls <= E <= embed_cap`, unconditionally.** Each distinct endpoint key resolves at most once inside one lifecycle — the corrected argument in Decision 2 shows every outcome of the first resolution leaves a live row that makes the repeat hit L0 — so the number of merge-gate resolutions that issue a request cannot exceed `E`, and `embed_cap = E + T + N >= E`.

That relation holds because of the deduplicated `E` key and because the counter is a resolution counter — not because of any candidate bound. **There is no longer any exception to it**: the alias exception recorded in the first revision of this spec was withdrawn as factually wrong (Decision 2), and no path is known on which a repeated key spends a second request. This holds for both lifecycle shapes, including the single-record promote lifecycle (Decision 1A).

**The counting seam (frozen, low blast radius).** The budget is threaded to the merge call and the counting is *structural*, not inferred at call sites:

1. `ExtractPersistDeps` (`persist.ts:60-87`) gains one **required** field, `mergeBudget`, carrying the lifecycle's budget handle. **Required is a compile-time guarantee, not a claim that every owner can pre-compute a cap value** — the first revision justified it with "every lifecycle owner constructs one", and that premise was false: the dashboard's `persistDeps()` returns only `{ embedder, logger, slotEmbedding }` (`maintenance.ts:62-70`) and feeds `promoteRecord` (`maintenance.ts:191`). The handle is therefore a three-state object, not a number: **unarmed → armed(`embed_cap`) → counting**, exposing `arm(cap)`, `countResolution()` and `snapshot()`. `countResolution()` **throws a typed error when the handle is still unarmed**, so an un-budgeted merge is impossible on every path rather than merely unintended — the property the required field was meant to buy, now enforced instead of asserted. Arming is always legal and happens exactly once per lifecycle, after the population is known and before the first resolution: in the extract lifecycle after phase E (Decision 1), and on the promote lifecycle between the payload parse and `persistOutputs` (Decision 1A).
2. `resolveEntity` wraps `deps.embedder` in the budget's **per-resolution counting proxy** at the merge-context construction and passes the proxy — `persist.ts:541-548`, the `embedder:` line is the only change. `deps.embedder` itself is untouched, so `embedEntityForWrite` (`persist.ts:562`, `:586`) and `vetRelationNorm` (`persist.ts:493-496`) keep the raw client.
3. **No `merge.ts` call site changes.** The proxy forwards `available` and `modelId` (`src/core/embedder.ts:14-28`) and `embed(texts)` verbatim, so `embedCosine` (`merge.ts:443`), `embedOne` (`merge.ts:412`) and `l3Cosine` (`merge.ts:390`) are untouched, and the merge module's signature stays locked.
4. **One resolution = one proxy instance = at most one increment**, raised on that instance's *first* `embed()` call. Every later `embed()` in the same resolution — the L2 per-candidate loop (`merge.ts:197-204`) and `l3Cosine`'s per-candidate embeds (`merge.ts:386-392`) — is forwarded and not counted.

**Counting rules:**

- **The increment happens before the request leaves**, and a request that then fails still counts (`merge.ts:411-417`, `merge.ts:445-448`). **No refund, ever** — including when the chunk's transaction later rolls back. The only writer of `embed_calls` is the resolution gate, and it only ever increments; there is no mid-lifecycle reset.
- **Not consumed** (and therefore not capped): the entity write embed (`persist.ts:562`, `:586`); the relation-normalization batch (`persist.ts:493-496` → `normalize.ts:81`); chunk-upstream and slot-dual-write embeds (the merge path bypasses the slot source, `persist.ts:545`).
- **Recorded consequence — the request amplification is out of budget by design.** One resolution can cost `C + 1` provider requests: the L2 gate embeds per same-type candidate and `l3Cosine` embeds every candidate lacking a stored vector, against a candidate set that is the entire non-retired entity store. This is a **cost and observability** concern, deliberately not the breaker's unit: bounding it is the blocking-subset candidate loader's job (`merge.ts:104-110`), which this spec does not decide. No raw-request counter is added — the frozen field list is `source_ref`, `embed_calls`, `embed_cap`, and a fourth field would have no reader.
- **`embed_calls` means "merge-gate resolutions that embedded", not "all provider requests" and not "all merge-gate requests".** This wording is load-bearing: `normalizeRelation` is a real embed this cap deliberately does not bound, and the L2 fan-out is real spend this cap deliberately does not bound.

### Decision 4 — breach: a run-level typed failure, not a chunk leg and not a skip

Exactly `embed_cap` merge-gate resolutions are permitted. The **(cap + 1)-th resolution is refused before it issues any embed request** — the proxy throws on its first `embed()` when `embed_calls >= embed_cap`, so a test can assert zero embedder calls at the refusal.

The breach is a **run-level failure** and must propagate as one:

- **It must not become a `failed` chunk leg.** `processChunk` is mark-and-continue (`pipeline.ts:344-370`, `pipeline.ts:472-514`); a breach sealed that way would be sealed as an ordinary extraction failure, and the code would surface as `batchFailureCode`'s first code (`pipeline.ts:308-311`) — an operator would read a cost failure as a source-content failure.
- **It must not degrade into a skipped candidate.** L2/L3 already have an embed-failure path that skips a candidate and falls through to `created-new` (`merge.ts:205-210`, `merge.ts:255-259`). Routing the breach there would publish a plausible-looking graph built from merges that were never proven.
- **Propagation path (frozen):** throw out of the merge context → the in-flight chunk's phase-C transaction rolls back (`pipeline.ts:440`'s leg) → re-throw past phase C → the index-job extract stage re-wraps it as `IndexJobStageError(ENTITY_MERGE_EMBED_LIMIT, …)` in the shape already used for `INDEX_JOB_EXTRACT_INCOMPLETE` (`index-job-worker.ts:347-351`) → `runIndexJob` publishes `failed` with that `failure_code` (`index-job.ts:107-109`). The re-wrap is required: an untyped throw reaches `index-job.ts:108`, is rethrown, and leaves the row `in_progress` and reclaimable (`index-job-worker.ts:263-271`) — the wrong outcome for a named, actionable failure.
- **The literal is exactly `ENTITY_MERGE_EMBED_LIMIT`**, the value fin already branches on (`fin/src/fin/corpus/demo_seed.py:175`, `:1718`).

### Decision 4A — the same breach on the promote lifecycle

The promote lifecycle has **no index job and no extract stage**, so the re-wrap in Decision 4 has no target there. The breach is nevertheless the same refusal, with the same literal, and it must not be absorbed:

- **It is a typed throw out of `promoteRecord`, not a promotion outcome.** The single transaction rolls back (`actions.ts:215-218`) and the record stays `failed` with its `proposed_payload` intact — the retry posture the function already documents (`actions.ts:111-112`). It is **not** folded into `commitSelfLoopRejection` (`actions.ts:183-197`), which is the promotion's own permanent-reject outcome (`SELF_LOOP_REJECTED_CODE`); a cost refusal is retryable, that one is not, and conflating them would put a re-runnable failure into the list operators are told never to re-run.
- **It is not a `PromotionRefusedError`.** Those carry code `INVALID_INPUT` (`actions.ts:37-42`) and mean "this record cannot be promoted" (missing row, not failed, discarded, no payload, unreadable payload, dead chunk — `actions.ts:133-174`). A budget breach is a cost refusal on a perfectly promotable record, and must carry its own typed error with the `ENTITY_MERGE_EMBED_LIMIT` code.
- **Surfaces, per entry, from the existing error plumbing — no new route, no new exit path:** the **CLI** lands it in `runCli`'s catch → `reportFatal` → exit 1, the same route the existing typed refusals already take (`cli/extract.ts:597-614`); the **dashboard** maps it through the shared `mapRunnerError` (`maintenance.ts:179-180`, `handlers/writes.ts:130`), which sends any non-`INVALID_INPUT` `GraphragError` to 503 `STORAGE_ERROR` (`handlers/writes.ts:116-118`) — the correct reading for "the system refused on cost", not a 400 caller mistake.
- **The breach line still carries the frozen three fields.** `source_ref` on this path is the **promoted chunk's** `source_ref`, so `promoteRecord`'s chunk read gains that one column (`actions.ts:164-167`); `chunks.source_ref` already exists and is already read from this table (`pipeline.ts:208`). A breach line whose `source_ref` were always `null` would satisfy the field list only in name.

### Decision 5 — partial effects, restart/reclaim, concurrency

- **Partial commit is allowed and is the honest outcome.** One transaction per chunk (`pipeline.ts:440`) means chunks committed before the breach stay committed and their `extraction_records` rows read `succeeded`; only the in-flight chunk rolls back. The rolled-back chunk's already-spent resolutions are not returned to the budget (Decision 3). A source-wide rollback is refused (ADR-0013).
- **Restart / reclaim starts a new lifecycle.** The budget is in-process state owned by one lifecycle. A job reclaimed after the lease window (`--stalled-after`, `index-job-worker.ts:125`, `:244-248`) runs a fresh lifecycle whose scope is the **still-pending** chunks — a chunk with a `succeeded` record no longer matches `PENDING_CHUNK_PREDICATE` (`pipeline.ts:101-103`), so it neither consumes nor inflates the new cap. Consequence, stated plainly in the ADR: the breaker bounds **one lifecycle**, so repeated re-runs of the same source each get a fresh cap.
- **Concurrency: the budget is a per-lifecycle value, never module state and never a database row.** It is threaded through the merge context, so two lifecycles cannot share a counter. Workers already serialize jobs under `JOB_SERIALIZATION_KEY` (`index-job-worker.ts:115`, `:259`), so one worker holds one live run; an MCP `extract` running in the server process alongside a worker run has its own independent budget. No lock and no shared state are introduced by this cap.

### Decision 6 — phase-E persistence, crash and reclaim (frozen)

**Scope: this decision governs the extract lifecycle only.** The promote lifecycle has no phase E at all (Decision 1A) — its population is a payload sealed by an earlier run, and its `BEGIN … COMMIT` / `ROLLBACK` envelope (`actions.ts:126`, `:208`, `:215-218`) is unchanged by this spec except for the arming point and the breach throw. Nothing below may be read as re-shaping `promoteRecord`'s transaction.

Today the `extraction_records` row (`pipeline.ts:442`), the method-conflict gate (`pipeline.ts:451`), the LLM call (`pipeline.ts:471`), the judge (`pipeline.ts:490`), `markFailedWithProposal` (`pipeline.ts:496`) and `persistOutputs` (`pipeline.ts:515`) all sit inside the single `BEGIN` at `pipeline.ts:440`. Phase E owns no transaction at all, so every artifact needs an owner. Frozen:

| Artifact | Phase | Transaction |
| --- | --- | --- |
| `extraction_records` row of an `ok` leg (`insertRecord`, `pipeline.ts:442`) | **C** | the chunk transaction, in the position it holds today |
| `extraction_records` row of a sealed-failed leg (`markFailed` `pipeline.ts:473`, judge `pipeline.ts:496`) | **E** | a dedicated single-row transaction opened and committed at the seal, exactly where `:477` and `:502` commit today |
| judge proposal payload (`markFailedWithProposal`, `pipeline.ts:496`) | **E** | the same dedicated transaction as its failed record |
| method-conflict refusal (`findChunkMethodConflict`, `pipeline.ts:451`) | **E** (early) and **C** (re-check) | E: the dedicated failed-record transaction, sealed as `failed` with `EXTRACT_METHOD_CONFLICT_CODE`. C: inside the chunk transaction, in today's position, sealing the same code and message |
| merge writes (`persist.ts:558-588`), triple upsert (`persist.ts:233-242`), gray-zone hold records (`pipeline.ts:530`), survivor enrichment (`pipeline.ts:563`), projection intents (`pipeline.ts:576`), method spine (`pipeline.ts:581`) | **C** | the chunk transaction, unchanged |

Consequences, all deliberate:

- **The LLM round trip leaves the write transaction.** Today the transaction opens at `pipeline.ts:440` and the LLM call runs inside it; under this decision the chunk's write transaction no longer spans a model round trip.
- **A sealed-failed leg's record is durable before phase C exists.** A crash during phase E loses only the `ok`-leg extraction work, never a failure record — which is the durability the maintenance lane and `listFailed()` depend on.
- **An `ok` leg that never reaches phase C** (page ceiling, crash, reclaim) leaves no record, so its chunk stays pending and is re-extracted — the same pending-ness rule as today (`pipeline.ts:101-103`).
- **The method-conflict gate runs in both phases.** Phase E's check exists only to avoid paying a model round trip for a chunk that will be refused; phase C's re-check keeps the guard at the commit point, so a concurrent writer cannot slip a second method claim in between. A conflict found in phase C seals exactly as it does today (`pipeline.ts:452-469`).

**Reclaim regression, declared.** During phase E nothing is persisted for `ok` legs, while the lease is 15 minutes by default (`index-job-worker.ts:125`) and `claimNext` reclaims through `stalledBefore` (`index-job-worker.ts:244-248`) — and the claim happens *before* the serialization lock is taken (`index-job-worker.ts:218`, `:259`). So a lifecycle whose phase E outlives the lease is claimed by a second worker, which blocks on `JOB_SERIALIZATION_KEY` while the first worker finishes; the first worker's terminal UPDATE is then rejected (it is guarded by the `started_at` it claimed, `pgvector-backend.ts:1804`) and the second worker re-extracts the source, **doubling the phase-E LLM spend**. Today's exposure is one chunk — one transaction, one model round trip. The new exposure is one source's entire phase E. **Accepted**, with the operator answer being `--stalled-after` (`index-job-worker.ts:183-196`), which is already a flag. The two alternatives are rejected here: a lease heartbeat needs a new touch path on the store and fights the `started_at` publish guard, and committing per page is the forbidden per-batch cap (Decision 1 (C)). A source whose phase E cannot finish inside the lease must have the flag raised; the breaker will not absorb that silently.

### Decision 7 — the observable surface is a log line, and only a log line

**Breach line.** Event `entity-merge-embed-limit`, level `error`, fields exactly `{ source_ref, embed_calls, embed_cap }`. `source_ref` is the opaque identifier already persisted as `index_jobs.source_ref` (`schema-bootstrap.ts:591`), so it is inside SC10 (`src/logging.ts:12-22`); no entity names, descriptions, evidence spans or chunk text are added.

**Completion line.** The per-lifecycle `extract-batch-complete` line (`pipeline.ts:371`) additionally carries `source_ref`, `embed_cap` and `embed_calls` at info. Without this, a deployment check could only observe the cap on a run that already breached, which is not a verification method (see Decision 9).

**No ledger column.** `index_jobs.failure_detail` is **not** added. `index_jobs` has `failure_code` and no detail column today (`schema-bootstrap.ts:589-598`); no consumer reads `embed_calls` or `embed_cap` from durable state — fin's port type carries only `failure_code: str | None` (`fin/src/fin/retrieve/index_job_port.py:177`, `:195`) and its classifier branches on `record.failure_code == ENTITY_MERGE_EMBED_LIMIT` (`fin/src/fin/corpus/demo_seed.py:1718`); and a column would force a migration *and* change `poll_index_job`'s wire shape (`src/tools/index-job.ts:47-48`) for zero read demand. The ticket requires logs, and logs are the whole surface.

**No `ceiling` alias.** The emitted names are exactly `source_ref`, `embed_calls`, `embed_cap` — the three the plan's field list already names. The ticket's "retain `ceiling` if a consumer still needs it" is conditional and **no consumer needs it**; the breaker has never been released, so no consumer ever read `ceiling`, and a removal trigger keyed on such a consumer would be unobservable. The earlier `ceiling` / `embed_cap` conflict was a conflict between two of this spec's own drafts, not a compatibility requirement.

**Both lifecycle shapes log the same three fields.** The breach line and the completion line carry `source_ref`, `embed_cap` and `embed_calls` on the extract lifecycle *and* on the promote lifecycle, so the cap is observable on a run that does not breach no matter which entry produced it. Concretely, `promote-record-complete` (`actions.ts:209-214`) additionally carries `source_ref`, `embed_cap` and `embed_calls`, with `source_ref` from the same chunk read Decision 4A adds; the breach line is identical in shape on both paths. No fourth field and no second field vocabulary — the whole point of the whitelist is that one reader parses both.

### Decision 8 — staging is bounded in bytes, and the scope refusal reuses the breaker literal

Phase E stages `{ chunkId, outputs }` per chunk and **does not stage the chunk text**. Phase C re-reads `chunks.content` by id inside its own chunk transaction, because two consumers in the commit path need it: the grounding gate compares the evidence span against it (`persist.ts:227`, supplied today at `pipeline.ts:519`) and `enrichStandardChunk` takes the chunk (`pipeline.ts:563`).

The bound is therefore on staged output bytes: `GRAPHRAG_MEMORY_ENTITY_MERGE_STAGE_MAX_BYTES`, default **67 108 864 bytes (64 MiB)**, measured as the serialized byte length of the staged outputs.

- **Why bytes and not chunk count.** The count ceiling this replaces was unreachable in production — the production scan page is `deps.batchLimit` (`config.ts:102`, default 100), so a chunk-count ceiling above ~100 could not be hit by the worker path at all — while the memory argument it justified was self-contradictory: at `DEFAULT_MAX_CONTENT_LENGTH = 100_000` chars per chunk (`extract.ts:33`), 1000 chunks is ~100 MB of chunk text alone. Staging only the outputs removes that term from the accounting entirely; the ceiling that remains bounds a payload that is orders of magnitude smaller than the text it came from. 64 MiB is far above any real source's extracted-output payload and far below a container memory budget.
- **When it is checked.** At every phase-E page boundary, before the next page's extraction. The page that crosses the ceiling has spent its own model round trips; nothing is committed, no merge has run, and the pages already staged are discarded with the lifecycle.
- **Refusal literal.** `ENTITY_MERGE_EMBED_LIMIT`, with the message distinguishing a **scope** refusal from a **cost** breach (it names the staged byte count, the ceiling, and the operator action — raise the knob or split the source). Reusing the literal is deliberate: fin's classifier branches on the code alone (`demo_seed.py:1718`), so the refusal categorizes correctly without a new fin class, and no new unclassified public literal enters the wire. The operator action is the same one a cost breach asks for, so one class is the honest shape.
- **Consequence.** A source whose extracted outputs exceed 64 MiB cannot be indexed in one lifecycle; the operator raises the knob or splits the source. Both pre-commit refusals (this one and the phase-E page ceiling) discard the lifecycle's staged work with nothing committed — accepted, because the alternative is a per-page cap.
- **The promote lifecycle stages nothing and is not subject to this ceiling.** It holds one payload that already exists in a row (`judge.ts:181-182`) and one chunk's content (`actions.ts:164-167`), both already resident; there is no page loop and no accumulation to bound. The ceiling is a phase-E memory guard, and a path with no phase E cannot trip it. Its only size bound is the existing record / chunk row.

### Decision 9 — deployment, build restart, and the ×50 record

- **Restart is required after the fix lands.** `runCli` is a drain loop inside a long-running worker process (`index-job-worker.ts:203`, `:215-228`); a rebuilt artifact changes nothing for a process still running the old build.
- **Runtime proof is one log field, not a source diff.** Because every lifecycle's completion line carries `embed_cap` (Decision 7), a live ×50 patch would show a 50× larger cap than the source-derived formula predicts. Proof is therefore: the built artifact's diff against `main` shows no multiplier **and** at least one observed run reports an `embed_cap` consistent with the formula.
- **×50 absence evidence, recorded 2026-10-16 at `ca0feeed` on `feat/qa-t2-entity-merge-embed-cap`.** Inspected: this repository's `src/**`, `tests/**`, `specs/**`, `docs/**`; `docker-compose.yml` (infrastructure services only — pgvector / Neo4j / Elasticsearch, no application service and no embed-cap environment variable); `.env.example` (embed keys only: base URL, model, dimensions, key aliases — no cap knob); `dist/` (**does not exist**, the package is not built in this worktree); and the fin worktree `src/**` + `specs/**`. Result: **no multiplier present.** The only `50` hits are a UUID version nibble `0x50` (`src/core/structured/identity.ts:473`, `src/core/storage/evidence-source.ts:350`), an unrelated "50–100-token" comment (`src/core/extraction/fast.ts:20`), and fin's 50 MiB upload cap (`fin/specs/corpus-serve-ingest.md:144`). `ENTITY_MERGE_EMBED_LIMIT` itself appears nowhere in this repository. **If a workaround is found at execution time**, it is removed from its real deployment/build location, the worker is rebuilt and restarted, and both the source diff and the running build are proven to use the original formula; absence at this commit is recorded as absence, not as removal.

## Open Questions

None blocking. Four are recorded as consequences rather than decisions, and none is reopened by implementation:

- **Evasion across lifecycles.** A source that breaches can be re-run and receive a fresh cap each time (Decision 5). Bounding that would require a durable per-source spend ledger, which is a separate ticket; this spec deliberately does not add one. The promote lifecycle inherits the same property: a breached promotion is retryable and re-derives the same cap, so it breaches again until the operator changes the source (Decision 1A).
- **The off-cap relation-normalization embed and the L2 request fan-out.** `normalizeRelation`'s batched request (`normalize.ts:81`) and the per-candidate L2/L3 embeds are real spend this cap deliberately does not bound (Decision 3). Bounding them is the candidate-loader's ticket, not this one.
- **The lease window vs phase E.** A source whose phase E exceeds the stalled-after window is re-extracted by a second worker (Decision 6). Declared and accepted there; a lease heartbeat is a separate durable-state change.
- **The withdrawn alias exception is withdrawn, not replaced.** `embed_calls <= E` now holds with no exception (Decision 2), and the only way it could stop holding is a future merge gate that materializes no row for the incoming surface form. If that ever lands, this spec's `E` definition must be revisited — recorded here so the withdrawal is not mistaken for an oversight.

**Does not decide:** the blocking-subset candidate loader, which `mergeEntitiesWithGating` still refuses (`merge.ts:104-110`), nor the per-source job reset boundary owned downstream by fin T3, nor any change to `resolveClosedSetTypes` / `isAliasSelfLoop` semantics — they stay module-private (Decision 2A).
